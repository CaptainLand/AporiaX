# 视觉能力与恢复审批修复

## 配置方式

在「设置 → 模型与 API」编辑 Provider，每个模型可单独选择图片输入能力：

- 自动：优先使用服务返回的能力信息，缺失时才使用兼容性的名称推断。
- 原生视觉：适用于具备图片输入能力但尚未被识别的灰测模型，例如用户自己的 DeepSeek 灰测接口。此选项仅声明能力，不保证上游 API 可用，也不会发起付费探测。
- 仅文本：显式禁止把该模型视为原生视觉模型。

模型 ID、名称、上下文窗口和能力设置会一起保存；重新发现模型时保留已手动指定的原生视觉/仅文本选项。旧的仅提交模型 ID 的保存请求也不会清除已有声明。

## 视觉代理与 Cloud

自配模型只使用已配置的自配视觉 Provider；界面展示与实际请求使用同一套选择逻辑，不会因存在 Cloud Provider 就偷偷改用 Cloud 额度。真正支持免密的本地 Provider 仍可使用。

Cloud 使用已登录 Desktop 会话请求 `GET /v1/capabilities/vision`，读取已启用模型和服务端凭据的配置就绪状态。模型名称来自服务端，不再写死 Qwen 或直接显示可用。接口不发起模型请求，不预占额度，不返回密钥。配置就绪不代表已经验证上游服务实际可调用。

未登录、旧服务没有此接口、超时或未配置时，桌面端显示尚未就绪/无法确认，且不会继续上传图片给该代理。当前 Cloud 改动位于 `apps/gateway/src/vision-capability.ts` 和 gateway 入口；需要后续更新、重启 Cloud 才能对正在运行的服务生效。本次未部署或重启 Cloud。

## 恢复审批

- 浏览器打开/关闭仍写操作日志，仍遵循普通权限策略，但导航错误不再作为未知写入污染后续恢复审批。旧版本留下的导航错误也会在恢复上下文中标记为可安全重试；原始审计结果保留。
- 历史记录只拦截相关操作（同操作指纹、同文件目标或缺少凭据的旧任务），不再拦截所有后续操作。
- 用户确认核对后，先持久化 `reconciled` 记录再继续。核对不等于上次操作成功，也不是永久放行。
- 本轮成功操作不会被当作历史重放反复询问；拒绝同一核对后，不会自动重新弹同一对话框。
- 并发 Agent 共用核对状态，等待确认不会卡住无关操作。祖先任务日志保持不变，包括超过 80 条上下文截取范围的历史记录。
- 发布、购买、文件变更等真正结果不明的副作用重试仍须核对；新发生的不确定操作不继承旧记录的核对结论。工作区外/目标不明删除及明确拒绝的工具边界保持不变。

## 验证

桌面端专项入口：`npm run test:vision-recovery`。覆盖 300 次操作无审批刷屏、旧任务恢复、并发确认、拒绝后重试、取消前未执行、SQLite 重开、祖先审计、模型元数据往返、就绪检查故障、浏览器中英文/明暗主题布局，以及真实 Electron 请求路由（网络响应模拟，无付费模型调用）。

Cloud：`npx --no-install tsx scripts/vision-capability-smoke.ts` 和 `npx --no-install tsc --noEmit -p tsconfig.json`。接口测试使用注入的鉴权、配置与模型记录，不依赖生产账号或数据库。
