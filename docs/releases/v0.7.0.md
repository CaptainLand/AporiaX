# AporiaX v0.7.0

AporiaX 0.7.0 introduces the first complete Aporia Account + Aporia Cloud desktop path while preserving the local-first Harness, BYOK providers, and local model workflows.

## Aporia Account and browser sign-in

- Added native browser authorization with PKCE S256, loopback callback validation, and one-time desktop authorization-code exchange.
- Access tokens remain in Electron Main memory only.
- Refresh tokens are encrypted with Electron `safeStorage` before persistence and rotate through the existing Cloud refresh flow.
- Renderer/preload receive projected Account state rather than raw access or refresh credentials.
- Signing in does not upload workspaces, project source, or local conversation data.

## Aporia Cloud managed models

Aporia Cloud now appears as a first-party model source beside user-configured APIs and local models.

- `DeepSeek V4 Flash` remains the default managed Cloud model.
- `DeepSeek V4 Pro` is available as a second managed Cloud model.
- Both use the authenticated Aporia Model Gateway and the same rolling weekly quota contract.
- Cloud model requests never require a DeepSeek API key in Desktop.
- BYOK and local providers remain separate and continue to use their own credentials/runtime paths.
- Weekly-quota exhaustion does not silently fall back to a paid BYOK provider.

## Native Cloud vision routing

Aporia Cloud adds image understanding without turning DeepSeek into a multimodal provider.

```text
image attachment
  -> Aporia Cloud vision (Qwen3.5 Flash)
  -> compact textual observation
  -> DeepSeek V4 Flash / V4 Pro
  -> normal Harness + tool loop
```

- Explicit image attachments are analyzed before the main Agent loop.
- Raw images are removed after the observation is materialized, so later tool rounds do not repeatedly resend or rebill the same image.
- Multiple images are analyzed independently.
- Qwen credentials and provider URLs remain Cloud-side; Desktop only uses the Aporia Account session and configured Model Gateway.
- User-configured providers keep their existing native/proxy vision behavior.

## Privacy-preserving free-tier installation identity

- Desktop creates one persistent random UUID per installation under Electron `userData`.
- The identifier survives sign-out/session rotation and is sent only during native Desktop token exchange.
- AporiaX does not read hardware serials, MAC addresses, Windows MachineGuid, disk IDs, or similar hardware fingerprints for this flow.
- Cloud HMAC-hashes the installation identifier before persistence and uses it only for free-tier anti-abuse / entitlement logic.

## Production-test polish

- Model picker source labels are now compact and source-specific: Aporia Cloud, Your API, and Local.
- Removed redundant capability strings such as `No API key required`, `Tool use`, `Vision`, and `Text only` from model rows.
- Local models are no longer presented as automatically image-capable; local vision still requires a configured visual model/runtime path.
- Model rows use a stable full-width layout so Flash / Pro / BYOK entries no longer jump between content-sized widths.
- Completed blue progress journals remain compact by default but now expand to the complete retained process with one click; there is no arbitrary pixel-height ceiling.
- Cloud connectivity failures stay quiet in the normal sidebar instead of filling the lower-left UI with repeated red network errors.
- External read-only references and built-in Word / Spreadsheet / Presentation design skills remain available from the previous production-test polish work.

## Release and packaging

- Package version is `0.7.0`.
- Node.js `>=22.12.0` remains the source requirement.
- Windows x64 remains the packaged desktop target.
- The 0.7.0 Windows installer and portable build are published separately from the source update.

## Known boundaries

- Aporia Cloud features require a reachable AporiaX Cloud deployment; BYOK and local providers remain usable independently.
- Local/offline image understanding is not automatic and depends on a user-configured local vision model/runtime.
- Scanned PDFs are still detected as requiring OCR, but AporiaX does not bundle an OCR engine yet.
- Full Cloud production deployment, domains, TLS, Redis/PostgreSQL operations, and provider budget configuration are server-side deployment concerns and are not bundled into the Desktop executable.
